## 第 1 步：抓列表 + 原文网盘链接
- 脚本：`scripts/fetch_full.js`（改 URL 里的页码）
- 输出：`data/pageXXX-full.json`
- 内容：每篇的 标题、文章URL、原文里的 百度网盘 / UC / 移动云盘 / 迅雷 / 夸克 / 115 链接
- 注意：只取正文列表区（`article` 标签的 10 篇），别扫全页 a 标签（会误抓侧栏）

## 第 2 步：抓"原文件分享名"
- 脚本：`scripts/fetch_real_names.js`
- 输出：写回 `pageXXX-full.json` 的 `realFileNames` 字段
- 作用：从原文网盘行的文本里精确提取真实分享名（如"孤儿""补习1.03"），用来对上你 CSV 里的短文件名
- 关键：网盘行形如 `百度网盘：孤儿 链接：https://...`，文件名写在冒号后；不要用侧栏/整页链接（会混入无关项）
- **有些页没有分享名**：网盘行只有"链接:https://pan.baidu.com/xxx?pwd=提取码"，此时 `realFileNames` 记成 `pwd:提取码` 和 `sid:链接ID`，匹配时改用提取码/ID 对应你的链接
- **读写要指同一页**：`fetch_real_names.js` 读哪页就写哪页，页号别写死（曾把 2395 的名字误写进 2394 文件，导致整页匹配全空）

## 第 3 步：你的分享链接（CSV 或 Excel）
- **必做**：抓完列表后先跑 `make_excel.js` 出待填表给用户（上次 2395 漏了直接让用户发 CSV，这是踩过的坑）
- **待填表固定 4 列**：`游戏标题 | 分享文件名 | PC端百度链接 | AZ端百度链接`，**只保留百度，不要 UC/移动云盘/迅雷/夸克/115 列**
- PC/AZ 双链接：C 列填 PC 端、D 列填 AZ 端（有标签按标签，没标签按原文顺序）；单链接只填 C 列
- `make_excel.js` 已按此生成（`pageXXX-full.json` 里 `baidu` 是带 label 的对象数组，`fetch_full.js` 顺序配对 PC/AZ）
- 用户两种方式任选：① 填好 xlsx 发我 ② 发导出的 CSV
- 用 `scripts/match_csv.js` 按 realFileNames 匹配（不要按标题模糊匹配）

## 第 4 步：部署（预览 → 确认 → 提交）
- 脚本：`scripts/deploy_pageXXX.js`
  - `node scripts/deploy_pageXXX.js preview` 先预览（写 `data/preview-XXX.md`，不改动）
  - 你确认后 `node scripts/deploy_pageXXX.js commit` 写入 `data/posts.json`
- 规则：
  - 只上"你的百度网盘链接"非空的文章，留空的不找、不上
  - 正文保留游戏介绍 + 内文图片（懒加载图用 `data-src`/`data-lazy-src` 兜底）
  - 下载区只保留「百度网盘：批次码 + 完整链接含 ?pwd=提取码」，其他网盘（UC/迅雷/夸克/115/移动云）一律删
  - 新增文章追加到 posts.json（id 接在最后一篇之后，旧数据不动）

## 第 5 步：预览确认

## 踩坑记录（2026-10-01 第2页批次）
1. **分享名在 h4 标签里**：旧 extractDriveLinks 只扫 div/p，但分享名（如 PCC247111/AZC247111）写在 h4 标签里，导致 name 全空。修复：扫描 h4,h3,h2,div,p。
2. **PCC 前缀被 PC/AZ 标签正则吞**：正则 (PC|AZ) 会匹配到 PCC247111 里的 PC，导致 curLabel 被设成 PC 但 curName 没设。修复：先匹配 4 位以上纯字母数字分享名，再匹配 PC/AZ 标签行（尾锚定）。
3. **fetch_full 没把 ?pwd= 拼进 url**：baidu 数组里的 url 是干净的，没有 ?pwd=，导致 make_excel 的 C/D 列提取码丢失。修复：fetch_full 抓完自动给 url 拼上 ?pwd=码。
4. **make_excel B 列只取 realFileNames**：旧逻辑 B 列 = it.realFileNames[0]，但第2页数据里 realFileNames 全 null，导致 B 列全是"原文码"。修复：B 列改为取 bds[].name（每个百度链接自带的分享名），双端用 " / " 连。
5. **Excel 被用户打开时写 EBUSY**：连续生成 v5→v11，每次 EBUSY 就换文件名。规则：写前先检查目标文件是否存在，被锁就换后缀。
6. **apply_patch 多行 context 匹配失败**：CRLF + 转义导致 context 行精确匹配经常失败，改用 delete+add（整文件重写）最稳。
7. **node -e 里复杂脚本被 PowerShell 吞**：一律写临时 .js 文件再跑，别用 node -e 内联复杂脚本。
8. **网站动态更新**：第2页的 10 篇标题/链接可能跟之前跑的不一样，每次抓前必须确认 page2-full.json 是最新数据，别用旧数据生成 Excel。

## 踩坑记录（2026-10-02 第2页重新抓取）
15. **wp_scraper 路径 bug：REST API 的 slug 是 URL 编码的**：WordPress REST API（/wp/v2/posts）返回的 slug 字段对中文是 percent-encoded 的（如 %e6%96%b0%e4%bd%9c...）。converters.py 的 _safe_name 直接把它写进文件名，Windows 下 mkdir 报 FileNotFoundError，导致约一半文章保存失败（10 篇里 5 篇挂）。修复：_safe_name 先 urllib.parse.unquote 解码，再过滤 Windows 非法字符。以后 wp_scraper 抓任何新页遇到"一半成功一半 FileNotFoundError"，先查 slug 是不是 URL 编码的。
16. **别拿旧数据当最新数据汇报**：站点每天更新，第 2 页上午是 13 篇（44616 开头），下午已换成 10 篇（44653 开头）。报标题/链接前必须实时重抓一遍（或直接打 REST API /wp-json/wp/v2/posts?per_page=10&page=2），不能读早上抓的 page2-full.json。
17. **双端识别用分享名前缀，不用"PC/AZ"正文标签**：双端文章的 h4 写「百度网盘：PCC254000」和「百度网盘：AZC254000」，前缀 PCC→PC 端、AZC→AZ 端、C→单端。正则直接找 PC|AZ 会把 PCC 里的 "PC" 误吞（旧坑 #2 的同类问题），务必先匹配 4 位以上纯字母数字分享名再判端。
18. **make_excel.js 输出文件名递增**：生成 xlsx 前先查目标文件是否被 Excel 占用，被锁就 v12→v13 换后缀再写，别直接 EBUSY。
19. **补抓失败的脚本要同时更新 .progress.json**：手动补抓（scratch/retry_failed.py 式）除了写 json 文件，还得把 .progress.json 里对应文章 status 改成 completed、failed 计数减一，否则下次续跑还会重抓这 5 篇。
